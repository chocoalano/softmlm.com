# Production deployment runbook

How mlmsoft goes from a commit to the live site, how to check it, and how
to back out. Background on the build output and the environment lives in
`docs/production-startup.md`; open items in `docs/production-blockers.md`.

## Source and trigger

- Repository: `github.com/chocoalano/softmlm.com`, branch `main`.
- Hostinger Node.js Web App, connected to that repository. Each deployment
  builds into a new `hbuilds/versions/{build-id}` folder; on success
  `hbuilds/current` is pointed at it and the output directory is synced to
  `public_html`. A failed build leaves the previous version running.
- `build/`, `public/assets` and `tmp/` are never committed: Hostinger builds
  from source. `.adonisjs/` is committed (generated types and the route
  registry, regenerated by every build).

| Setting | Value | Evidence |
| --- | --- | --- |
| Framework | Other | AdonisJS is not a listed preset |
| Node.js | 24.x | `engines.node` is `>=24`; AdonisJS 7 |
| Root directory | empty (folder with `package.json`) | |
| Build command | `npm run build:hostinger` | `node ace build`, then migrations (below) |
| Output directory | `build/public` | With `build`, `/package.json`, `/config/app.js`, `/start/env.js` and `/bin/server.js` were publicly downloadable on mlmsofts.com (2026-10-01) |
| Entry file | `server.cjs` | Hostinger's lsnode.js `require()`s the entry; `build/bin/server.js` (ES module, top-level await) failed with `ERR_REQUIRE_ASYNC_MODULE` → HTTP 503 (2026-10-01) |

Hostinger documents the entry file of the Other preset as relative to the
root directory, so `server.cjs` is the root wrapper; it loads
`build/bin/server.js` with `import()`.

## Before pushing

```sh
npm run lint
npm run typecheck
PORT=3335 node ace test     # never the developer's port 3333
npm audit
```

Review `git status` and `git diff` before committing: no `.env`, no
`*.sqlite3`, no `*.zip`, no QA data or dummy WhatsApp number.

| `WHATSAPP_MARKETING_NUMBER` | the real sales number, international format; empty → WhatsApp buttons fall back to the forms (blocker #9) |

socket LiteSpeed gives it.

## Migrations

`npm run build:hostinger` runs `node build/ace.js migration:run --force`
inside the new version's folder, before that version receives traffic:

- a failing migration fails the build, and the previous version keeps
  running;
- only pending `up()` methods run. Deployment never runs
  `migration:fresh`, `migration:reset`, `migration:rollback` or seeders
  (there are none), and never clears data;
- the old version keeps serving while the migration runs, so a migration
  must leave the schema usable by the previous release.

**Trade-off.** Automatic migration is acceptable while migrations are
additive (new tables, new nullable columns). **Breaking or destructive
migrations (dropping or renaming a column, changing a type, rewriting
data) require controlled deployment planning:** a backup taken and
checked first (blocker #6), the change split into an additive release and
a later clean-up release, and a deploy outside business hours. Example in
the history: `1790800000000_add_lifecycle_and_attribution_to_demo_requests`
copies `modules` into `selected_modules_snapshot` and then drops `modules`.
It is harmless on a new database but would be a breaking change on a live
one.

To run migrations by hand instead, use build command `npm run build` and,
over SSH from `hbuilds/current`, `node build/ace.js migration:run --force`.

## Smoke test after a deployment

Replace the domain if needed. Use QA identities clearly marked as QA
(`qa+…@…`, name "QA test") and delete or mark those leads afterwards.

1. **Server files are not public** (each must not answer 200):
   `/package.json`, `/config/app.js`, `/start/env.js`, `/bin/server.js`,
   `/.env`.
2. **Pages** answer 200 with a `Content-Security-Policy` header: `/en`,
   `/id`, `/en/pricing`, `/id/pricing`, `/en/compensation-plans`,
   `/en/how-we-do-it`, `/en/services`, `/en/integrations`, `/en/security`.
   An unknown path answers 404.
3. **Assets**: JS, CSS, fonts, favicon and logo load; the page source has
   no `localhost`, `:3333`, `:3334` or Vite dev-server URL.
4. **SEO**: canonicals and hreflang use the production domain.
5. **Forms**: the consultation form and the demo form create a lead in the
   back office; the sales inbox receives the notification and the visitor
   the confirmation (blocker #5).
6. **WhatsApp**: with a number configured, the button opens `wa.me` with
   the right number, the EN/ID message and a reference; without one, the
   button falls back to the form.
7. **Back office**: login, an authorised page, logout; the previous
   session no longer opens the back office; a `marketing` user cannot open
   leads.
8. **Runtime logs** in hPanel show no errors.

## Rollback

- **Application:** redeploy the previous release. Prefer `git revert` of
  the bad commit and a normal push, so `main` stays the truth. This is safe
  when the schema is still compatible with the previous release, which is
  why migrations must be additive.
- **Do not** run `migration:rollback` in production as a rollback step:
  `down()` methods drop tables and columns, which deletes data.
- **Database restore** only when data is actually damaged, from a verified
  backup, as a planned operation (blocker #6: backups and a tested restore
  are not in place yet).

## Database cautions

- Production uses MySQL; SQLite inside the app folder is lost at the next
  deployment.
- The engine Hostinger provides (MySQL 8.x or MariaDB) and its version must
  be read from phpMyAdmin (`SELECT VERSION()`) and recorded; MariaDB is not
  verified (blocker #17).
- No restore has been tested yet (blocker #6).

## Local QA policy

- The developer's server runs on port 3333. QA uses its own port (3334 for
  a production build, 3335 for the test suite) and stops only the process
  it started: no `pkill`.
- QA writes only rows it can identify (QA-tagged) and removes only those.
