# Production blockers

Items that must be resolved before staging/public release. A blocker is
closed only with evidence (a test, a configuration check, or a documented
verification run). Last updated: 2026-10-01 (Phase 10).

| # | Blocker | Why it blocks | Status |
|---|---|---|---|
| 1 | **Public `/signup`** (starter kit) | mlmsoft is not a self-service product. Anyone can currently create an account. Staff accounts must be created through a controlled flow. | Open — audit and disable before staging (Phase 17) |
| 2 | **`trustProxy` behind Cloudflare / reverse proxy** | Without it every visitor shares the proxy IP: one rate-limit bucket for everybody (the lead form and the `/marketing/events` collector alike), and wrong IP hashes on leads. Arbitrary `X-Forwarded-For` must not be trusted either. | Open — configure and test through the real proxy (Phase 21/22) |
| 3 | **Durable queue for lead emails** | Lead emails are currently delivered in the background of the web process. Acceptable for development only: a crash loses pending emails (the lead itself is safe). Target: request → DB commit → persistent queue → mail worker → SMTP, with retry/backoff, failed-job visibility, graceful restart and idempotency. | Open — infrastructure phase |
| 4 | **Production database on MySQL 8** | Production and staging must not use SQLite. Separate databases and credentials per environment. The code has no MySQL connection configured yet (`config/database.ts` is SQLite only, `mysql2` is not installed). | Open — Phase 18/21. See #17 for what has been verified on MySQL so far |
| 5 | **SMTP provider and sales inbox configured and tested** | `SALES_NOTIFICATION_EMAILS`, SMTP host/port/credentials/encryption and the from-address come from environment only. Must be verified end to end in staging and production. | Open — waiting for provider |
| 6 | **Automated MySQL backups + a tested restore** | No disaster-recovery claim until a restore has been performed and recorded on non-production. | Open — Phase 20 |
| 7 | **Monitoring hooks** | Application errors, HTTP 5xx, queue failures, mail failures, DB connectivity and uptime need a destination. Provider to be decided. | Open — Phase 19 |
| 8 | **Marketing claims audit** | Every public page (home, compensation, pricing, who-we-serve, role pages, features overview, the three feature pages, how-we-do-it, the services hub and the five service pages, the Integrations page) is covered by the automated claims gate in **English and Indonesian**, and no unverified provider name may appear in any of them (`tests/unit/integration_evidence.spec.ts`, list in `docs/integration-evidence.md`) (`tests/unit/claims_gate.spec.ts`, including every file in `inertia/i18n`). A functional test fails if a new public page is added without its source being scanned. Full sweep in Phase 24. | Partially closed — all current public pages pass in both languages |
| 9 | **Sales WhatsApp number** | `WHATSAPP_MARKETING_NUMBER` must hold the real sales number (international format). Without it every WhatsApp button falls back to "Talk to our team" → the demo form, which is safe but not the intended primary conversion. A production configuration blocker, not a development blocker. | Open — waiting for the number |
| 10 | **Final native review of the Indonesian copy** | All marketing copy exists in Bahasa Indonesia, written for Indonesian owners and checked against the glossary (`docs/marketing-i18n.md`) and the claims gate. A native Indonesian marketer at mlmsoft should still read every page once before launch; lines flagged during Phase 7 are listed in the Phase 7 report. | Open — review before public launch |
| 11 | **Final light/dark visual review on real devices** | Both themes are built on semantic tokens and were checked in headless Chromium at 360–1440px (EN/ID × light/dark). A pass on real iOS Safari and Android Chrome, in both themes, is still needed before launch. | Open — review before public launch |
| 12 | **`APP_URL` must be the production https origin** | Canonical and hreflang URLs are built from `APP_URL`. A wrong value in production publishes wrong canonicals for every page in both languages. | Open — verify in staging and production |
| 13 | **One brand name across logo and copy** | The name the site prints is centralised in `shared/brand.ts` (`MARKETING_BRAND_NAME` = "mlmsoft"): SEO titles, the page-title template, WhatsApp messages, mail settings and the email copy read it, and a test fails if any brand mention in the marketing copy differs from it. Remaining inconsistencies: (1) the logo artwork (header, footer, admin, favicon) reads **"mlmsofts"**; (2) the email header wordmark in `resources/views/emails/layout.edge` still reads **"SoftMLM"**; (3) the copy in `inertia/i18n` spells "mlmsoft" as text, so a rename is a search-and-replace guarded by that test; (4) email footers name the domain **mlmsoft.com** while the project folder is `softmlm.com`; (5) the logo image files are named `mlmsofts-*.png`; (6) the tracking cookies are named `mlmsoft_visitor`, `mlmsoft_visit` and `mlmsoft_tracking` (`config/marketing_tracking.ts`): renaming them later starts every returning visitor as a new one, so decide before launch. Nothing was renamed in Phase 9 or 9.5. | Open — brand owner to confirm the name and domain; then the artwork, the email header and the copy change together |
| 14 | **Product Maklon Claims Review** | The public offer is VERIFIED and a public provider disclosure is not required by business decision (`docs/product-maklon-evidence.md`). Every specific (categories, formulation, certifications, BPOM/Halal, MOQ, lead time, capacity, prices) is still UNVERIFIED and may only appear as "discussed for your product". Before launch, a claims review confirms the page still makes no capability claim beyond the offer, and any specific the business wants to state gets evidence first. | Open — claims review before public launch |
| 15 | **Commercial terms for the growth services** | Service pages say "pricing depends on scope" and show no packages. Sales needs an agreed way to scope and price social media, SEO, advertising, branding and maklon before those leads arrive in volume. Not a publication blocker for the pages themselves. | Open — commercial decision |
| 16 | **Privacy notice and tracking consent** | Phase 9.5 adds first-party visitor tracking (`docs/marketing-attribution.md`): a random visitor cookie (90 days), a visit cookie (30 minutes), page views and a few interaction events, WhatsApp intents with a reference in the prefilled message, and a lead's frozen attribution snapshot when the visitor submits a form. The site has **no privacy notice page** yet. Before public launch, legal/business must: publish a privacy notice (EN + ID) describing the cookies, the events, the lead link, retention and the opt-out; decide whether the tracking needs prior consent under UU PDP (UU 27/2022) for the target markets, or can rely on the notice plus opt-out. The code already supports turning tracking off (`MARKETING_TRACKING_ENABLED=false`), honours Global Privacy Control and an opt-out cookie; a consent banner, if required, is not built. | Open — legal/business decision and privacy page before public launch |
| 17 | **Tracking and JSON queries verified on MySQL 8.0** | Development and tests run on SQLite, and the lead interest filter uses dialect-specific JSON functions (`JSON_LENGTH`/`JSON_CONTAINS` on MySQL). Verified on 2026-10-01: all 10 migrations (up and down, including the WhatsApp intents / attribution snapshot migration) and the **full test suite (209 tests, Phase 10) pass on a throwaway MySQL 9.6.0** instance (default `sql_mode` incl. `ONLY_FULL_GROUP_BY` and `STRICT_TRANS_TABLES`, utf8mb4), run from a scratch copy of the project. That run found and fixed one real bug: Knex's `whereLike` adds `COLLATE utf8_bin`, which fails on utf8mb4 columns (admin lead search and visitor search now use a plain `LIKE`). MySQL **8.0**, the production target, has not been run; 9.6 is the closest available and shares the relevant behaviour, but it is not the same server. | Partially closed — repeat the suite on MySQL 8.0 in staging (Phase 18/21) |
| 18 | **Scheduled retention cleanup** | Anonymous tracking data is kept for `MARKETING_ANONYMOUS_RETENTION_DAYS` (default 365). `node ace marketing:cleanup --apply` deletes older anonymous data (never leads or their attribution snapshots, never a visitor linked to a lead, never a WhatsApp intent sales confirmed or linked) but nothing runs it yet. The production retention period must be set with the privacy notice (#16). | Open — schedule it (daily cron or the scheduler chosen in the infrastructure phase) |
| 19 | **Business definition of "customer"** | The pipeline is Visitor → Intent → Lead → Qualified → Converted → Customer, but no one has defined when a converted lead becomes a customer (signed contract, first payment, go-live). Until then the back office never shows or counts customers, and no customer record exists. | Open — business decision before the CRM phase |

## Safeguards already in place

- Tests refuse to start unless the database is clearly a test database
  (`tests/support/database_guard.ts`, covered by `tests/unit/database_guard.spec.ts`).
- The test environment uses its own SQLite file (`tmp/test.sqlite3`).
- `nodemailer` is pinned to a patched 10.x through `overrides`; production must run Node.js 20 or newer. Do not downgrade it.
- QA fixtures are never seeded; QA accounts are created manually and removed after use.
